## v2.17.1（导入修复 + 屏蔽词上限修复 + 微交互）

### 历史记录导入提示「文件里没有可用的记录」（换电脑后导入导出的文件）

- 根因：导出时 `removed: lastAll.map(({ id, ...r }) => r)` 把每条记录的 `id` 去掉了，而导入的 `normalizeRemoved` 又要求每条必须有 `id`，于是用本插件自己导出的文件再导入，所有记录都被当成无效丢弃。导出与导入的约定不一致，与是否换电脑无关。数据包里的 `removed-log-anonymized.json` 就是这种导出文件，可直接复现（1232 条全被拒）。
- 处理：导入不再要求 `id`；缺失时按「账号 + 时间 + 评论文本」生成稳定的 id（`imp-…`），同一份文件重复导入会按 id 去重，也不会因为 id 为空被后台按 `id|src` 合并成一条；导入前按时间从旧到新排序，后台逐条放到最前，最终新的在上面。提示写明文件条数、新增数和重复数。
- 验证：两个相互独立的浏览器环境，A 导出记录 / 名单 / 屏蔽词，B 全新环境导入，数量与「手动」标记都一致；数据包导出文件导入新增 1228 条（文件内有 4 条完全重复），再导一次新增 0。

### 屏蔽词上限不一致

- 输入框与说明都写「最多 500 个」，识别引擎也按 500 编译，但设置面板的添加和导入在 100 个就停了，批量导入超过 100 个会被截断，还提示「已到 500 个上限」。处理：统一用常量 `WORDS_MAX = 500`（测试：导入 300 个全部加入；已有 450 再导入 200 个，加到 500 为止并提示）。

### 参考「UI Moments」微交互图的改动

- 悬浮台展开列表的「不是 / 放过」：由两个纯文字按钮改为带图标的小胶囊（对勾 / 箭头），放在账号名那一行右侧，鼠标移到该行或键盘聚焦时才出现；收起状态的单行只留一个对勾图标按钮。点击后该行先划线并收起（参考 Checklist），0.24 秒后再执行放行。
- 嫌疑分在展开列表里由百分比改为 5 颗圆点（每 20% 一颗，≥4 颗为红色，参考 Pebble Rating），具体百分比放在悬停提示里。
- 设置面板：标签页和分段控件的选中底板改为滑动的滑块（参考 Gooey Tab Bar）。各段等宽，滑块位置只由 `--i`（第几段）决定，不需要测量，面板隐藏时也正确；灵敏度滑块在三档预设（70% / 60% / 50%）位置加刻度，拖动时滑块放大（参考 Detent Dial）；开关按下时拉长（参考 Stretch Toggle）；「连接中」和空间卡片的「DeepSeek 分析中」加旋转的加载圈。
- 悬浮台面板展开时从圆钮方向缩放出现（参考 Menu Morph），动画都遵循 `prefers-reduced-motion`。
- 评估后没有采用的：Paper Plane、Squash Play、Flip Coin、Scrub Wave、Elastic String 等纯装饰性的，与插件场景无关；Odometer（计数滚动）、Tide Progress / Download Ring（空间卡片分数环）、按住确认（用于「清空」）列为可选项，等用户决定。

## v2.16.8（保留长评论 + 导入修复 + 文案重写）

### 名单导入没有任何提示（换电脑导入「显示不行」）

- 根因：`io-import` 的成功提示里引用了没定义的变量 `nb` / `nw`（应为 `r.nb` / `r.nw`），名单其实已经合并进去，但随后抛 ReferenceError，提示条和导入日志都没出现，用户看到的是毫无反应。该 bug 一直存在，不只是新电脑。
- 处理：两个导入入口合并成同一套流程（读文件去 BOM → 识别 → 合并 → 提示），整体 try/catch，任何失败都显示原因；认不出格式时显示文件顶层字段名；导入时保留「手动」标记（原来 normalizeList 会丢掉 `m`）；历史记录入口导入名单文件时也会显示结果。底部新增「在新标签页打开」：个别环境选文件时会关掉弹窗，导入不会完成，在标签页里没有这个问题。
- 验证：旧代码上复现（含导出格式、BOM、纯数组、{mid:昵称}），新代码六种情形都有明确提示。

### 界面文案重写

- 问题：「这里管三件事」「命中即隐藏，不打扰」这类总结腔、对仗句、宣传语太重。
- 处理：popup、悬浮台、空间卡片、提示条、manifest 描述、README、审核须知的说明文字全部改成直白短句；名单页去掉说明卡片，改叫「已屏蔽账号」「放行账号」「本页隐藏记录」「历史隐藏记录」；拉黑提示去掉「特征强化」等内部术语。README 重写为短版，保留对两个上游项目的致谢。

### 保留「长且不像 AI」的评论（设置里可关，默认开）

- 需求：有些评论明显是 AI 写的，但质量高，不想直接屏蔽。最初设计了「标记」功能，后改为更小的方案：在判定里加一条豁免。
- 规则：评论超过 60 字（去掉「回复 @xx」、@提及、[表情]、空白后），且文字里命中的 AI 特征合计 < 10 分（不含「评论偏长」的加分）→ 即使账号被判为鱼也保留。不保留的情形：手动拉黑的账号、命中自定义屏蔽词、DeepSeek 认定 AI（≥70）。
- 实现：`comments.js` 的 `keepIt()`（文本部分每条评论只算一次，缓存在 `it.weak`）；doRender 判鱼前先过它，也不会因此把账号写进自动名单；`verdicts` 消息新增 `k`（要保留的 rpid）给主世界预隐藏跳过；接口层对「自动累积条目 + 长文本」放行给 DOM 层逐条判，手动条目照拦；规则新增 `kl`；设置项 `keepLong`（默认 true）。
- 取舍：长评论本身是机器人的常见特征，所以阈值保守（只有文字里几乎没有 AI 特征才留）；想更激进可调 `KEEP_MAX` / `KEEP_LEN`。关闭开关即恢复原行为。
- 已知副作用：自动名单账号的长评论不再被接口层直接删掉，改走「预隐藏」路径，依赖主世界与隔离世界的消息往返先于首屏渲染（与引擎新发现的鱼同一条路径）。

### 识别灵敏度（原「鉴定严格度」）方向与文案

- 问题：popup 滑块最右标「严格」却对应隐藏门槛 80%（最难隐藏），与悬浮台预设「严格 = 50%」方向相反；说明文字只讲分数，不讲后果。
- 处理：统一为「严格 = 稍有痕迹就隐藏 = 门槛低」。滑块向右 = 更严格 = 门槛更低（存储的仍是 threshold，界面用 `45+80−t` 映射）；标题改「识别灵敏度」，显示「标准 · 门槛 60%」；说明改为「嫌疑分达到 N% 就隐藏；(N−25)%–(N−1)% 只标可疑。越严格门槛越低：稍有痕迹就隐藏但误杀更多；越宽松：只隐藏证据确凿的」。悬浮台预设的 tooltip 同步说明。

### UP 主规则：接口层与 DOM 层统一，自动判定不动 UP，明确操作优先

- 问题：UP 豁免只是判定里的「评分 −40」，而接口层按屏蔽名单直接删评论、先于 DOM 层；UP 若在名单里（别处被自动累积 / 被误判），自己视频下的发言整条被删。反过来，UP 若真是机器人，悬停拉黑按钮又对 UP 禁用，用户没有顺手的办法屏蔽它。
- 规则：名单条目新增来源标记 `m:1`（用户明确操作：悬停按钮 / 框选 / 徽标「拉黑」/ 空间卡片「屏蔽此账号」）。UP 主本人：**自动累积的名单条目不生效**（判定层 judge 与接口层 hit 同一条规则；引擎也不再把 UP 自动写进名单），**手动条目照常生效**；悬停按钮对 UP 开放。自动条目被用户明确拉黑时升级为手动。旧数据没有 `m` 标记，一律按自动处理（旧的手动拉黑 UP 会变成不生效，需要再拉黑一次，影响面很小）。
- 接口层：规则新增 `bm`（手动条目 mid 集合）；UP mid 优先取评论接口自带的 `data.upper.mid`，比页面状态更早可用；该值也作为 `upMid` 回传隔离世界的兜底。
- 自定义屏蔽词命中仍然对 UP 生效（用户明确规则）。

### 悬停「拉黑」按钮「大多数时候不生效」的根因与重写

| # | 根因 | 处理 |
|---|---|---|
| 1 | **文档级 `mouseover`/`mouseout` 委托在评论区内部收不到事件**：B 站评论是嵌套 shadow DOM，DOM 规范规定 target 与 relatedTarget 在 document 层重定向后相同（都是 `<bili-comments>`）时不向 document 派发，所以鼠标在评论之间移动时，document 级 mouseover 根本不触发（实测：三条评论间移动只有 mousemove）。旧的疑似徽标悬停提示同样受影响（只有从评论区外进入时才触发，移开后也可能不收起） | 改用 `mousemove` + `composedPath()[0]` 去重；提示与按钮共用同一个监听 |
| 2 | 自动档要求「AI 话题或本页已有判鱼」才插入按钮，多数视频一个按钮都没有 | 取消这个门槛：自动档 = 停留 1 秒后出现；常开 = 立即出现；关闭 = 不出现 |
| 3 | 按钮是塞进 B 站评论 shadow DOM 的节点，靠 CSS `:host(:hover)` + 过渡延迟显隐；B 站重绘会冲掉外来节点，而我们只在有新数据时才补回 | 改为全页唯一的浮动按钮（`<dfy-blk>`，挂在 body），位置每次现算（昵称行右侧，有疑似徽标则在徽标之后），不依赖评论内注入的节点 |

行为规格：停留计时由 JS 控制（`BLK_DWELL`：auto 1000ms / on 0ms）；切到另一条评论立即收起并重新计时；滚动收起；鼠标离开窗口收起；UP 主自己不出按钮；点击后按钮变「撤销」并带 3 秒倒计时，期间评论保持可见、按钮常驻跟随，倒计时结束评论隐藏、按钮消失；点「撤销」恢复。

> 验证：无头 Chrome + 模拟评论区（真实 comments.js），覆盖 auto/on/off、0.4s 不出现、1s 后出现、切换评论、点击拉黑、撤销、3.3s 到期、移开收起，全部通过；**仍需在真实 B 站页面验证**（模拟 DOM 的层级是按源码推断的）。

### 评估意见核实（外部评估对「全页浮动按钮 + mousemove」方案提出的 4 点）

| 意见 | 核实结论 | 处理 |
|---|---|---|
| 1. 评论在屏幕边缘时按钮可能被挤出屏幕 | 部分成立：位置已做视口钳制（x/y 各留 8px），但昵称行只露出一半时钳制后按钮会脱离评论悬在边缘 | 昵称行未完整落在视口内时不出按钮 |
| 2. 全局 mousemove 性能开销 | 方案并不「按坐标反推」或遍历评论 getBoundingClientRect，而是直接取 `composedPath()`（浏览器已完成命中测试）并按最内层节点去重；矩形只在出现按钮时、以及撤销倒计时内每 250ms 算一次；监听为 passive。实测 6–11 µs/次 | 无需额外节流；不加 rAF（composedPath 必须在派发期间读取，无法延后） |
| 3. 楼中楼识别精度（坐标重叠） | 不适用：识别靠 `data-dfy-rpid` 属性沿事件路径取最近者，与坐标/高度无关；回复自带属性，先于主楼命中。已实测：悬停楼中楼回复，按钮出现在该回复昵称行，点击拉黑的是回复者 UID（不是主楼） | 无 |
| 4. 没提防抖机制 | 已有：同一评论去重、1s 停留计时、离开 250ms 宽限、切换评论立即重置计时、滚动收起 | 文档补充说明 |
