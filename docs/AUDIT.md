# DeepSieve 体检报告（2026-11-17，基于 v2.16.6，修复已并入 v2.16.7）

> 方法：通读全部 JS（background / storage / content / main-world / comments / detector / counter / bubble / space / popup），对每个怀疑点先**实测**再下结论。
> 环境：无头 Chromium + 模拟 B 站评论区 DOM（嵌套 shadow DOM，结构按源码推断）+ 合成评论数据；存储开销用 Node 按真实数据形状模拟。
> 数字是量级参考，不是真实页面的绝对值；**真实 B 站页面上的行为需实机确认**。

## 1. 先说结论

引擎本身比预期健康：内存与 CPU 都随评论数线性增长，没有发现泄漏或二次方热点。真正值得改的是 6 处小问题（已修），其余怀疑点实测后**不建议改**（避免过度设计）。

## 2. 实测基线（合成数据：3000 条评论 / 约 1200 账号 / 2000 个线程）

| 项目 | 实测 | 判断 |
|---|---|---|
| 评论引擎内存（items + accounts） | 约 0.7 KB/条，3000 条 ≈ +2.1 MB | 线性，可接受 |
| 每批 20 条新评论的处理 | 约 1–2 ms | 可忽略 |
| `doRender`（遍历全部线程） | 200→2000 线程：0.9 → 10 ms，线性 | 目前不卡；见 §5-A |
| 全局 `mousemove` 处理 | 4–7 µs/次 | 可忽略 |
| 主世界空闲轮询扫描（已标记） | 2000 线程约 4 ms / 1.5 s ≈ 0.25% CPU | 可忽略；后台标签页已停（§3-6） |
| 头像蓝色分析（canvas） | 0.05 ms/个，复用画布 0.02 ms；1200 账号合计约 60 ms | 可忽略 |
| 前科 `seen`（满额 6000）/ 精判缓存 `llmCache`（满额 3000） | JSON 600 KB / 170 KB，解析后堆 ≈ 2.7 MB/标签页 | 满额才到，常见远低于 |
| 屏蔽名单 5000 条 | 526 KB；后台单次写 5 ms；每标签页收到克隆 4 ms | 现实规模下可接受 |
| 一次「全量重判 + 全量重扫」（3000 条页面） | 约 30 ms/标签页，并跨世界传 689 KB | 见 §3-2 |

## 3. 已修复（6 项）

1. **前科 / 精判缓存每次保存都整表读写两份**（满额时单次约 15 ms，且每次写入向所有标签页广播新旧两份完整值，每个标签页约 10 ms）。
   → `memory.save()` 只读写有变化的那个键（测试：只改前科→只写 `seen`；只改精判→只写 `llmCache`；都改→两个）。
2. **屏蔽名单每新增一条（含本页自动累积），每个标签页都做全量重判 + 主世界清标记全量重发所有评论**（≈30 ms + 689 KB）。
   → 做差集：纯新增只重判新增账号（`rejudgeMids`，3 个账号 0.7 ms），规则下发带 `rescan:false`，主世界不再清标记重扫；有移除 / 白名单 / 屏蔽词 / 设置变化仍走完整路径（测试覆盖 5 种情形）。
3. **撤销窗口时序**：撤销窗口原本在写名单的 `await` 之后才登记；若存储事件先于后台响应到达，评论会先隐藏再弹回（实测旧代码窗口内出现「隐藏→显示」，新代码无变化）。
   → 窗口在写名单之前登记。
4. **换页不清理**：SPA 切视频时只有计数条归零，悬浮台「最近隐藏」仍挂着上一个视频的记录，`items / accounts` 只增不减；且换页判定用整条 `href`，点击评论永久链接（`#reply…`）会把计数清零。
   → 判定改为只看 `pathname`；换页时 `resetPage()` 清空旧页数据并让主世界重送当前 DOM 评论。注意：换页检测走现有 1 秒轮询，若新页面首批评论比轮询先到，会被清掉后由 `rescan` 补回（已测 `resetPage` 本身与路径判定；该竞态靠 rescan 兜底）。
5. **插件停用时仍对每个评论接口响应做克隆 + 解析 + 打分**。→ 停用时 fetch / XHR 钩子直接放行，零处理。
6. **后台标签页仍每 1.5 秒扫描一遍评论 DOM**。→ `document.hidden` 时跳过。

## 4. 评估后不改（附理由）

| 怀疑点 | 结论 |
|---|---|
| 悬浮台菜单每 1.5 秒整块重渲染、吞点击 | 核对后**不成立**：已是签名对比 + 定点更新 |
| 头像分析可按分数跳过以省请求 | **不能跳**：头像最高 +22 分，会改变「可疑」区间和 DeepSeek 候选门槛（离线分 ≥10/20），跳过会改变判定与精判调用量 |
| 4 个轮询定时器（content 1 s / counter 1 s / bubble 1.5 s / main-world 1.5 s）改事件驱动 | 每次耗时微秒级，后台标签页被浏览器节流；改动触及 4 个文件，收益不抵风险 |
| 名单改成逐键存储（每个 mid 一个 key） | 5000 条才 526 KB，写放大成本低；数据模型迁移风险高（导出格式兼容、popup 全量读取） |
| `DFY.callouts` / `refreshBurst` 每批 O(N) | 理论二次方，实测 3000 条时整批处理仅 2–4 ms，不构成瓶颈 |

## 5. 架构层面的选项（需要你决定，现阶段不建议做）

- **A. 增量渲染**：`doRender` 目前每次遍历全部线程（线性，2000 线程约 10 ms）。若你经常把评论区翻到 3000+ 线程，可改成「只处理新增线程 + 判定变化的账号」，需要主世界同步带回元素标识。收益只在超长评论区。
- **B. 前科 / 精判缓存归后台单一持有，页面按需查询**：每标签页省约 2.7 MB（满额时），并彻底消除跨标签广播；改动大（读取变异步，`absorb` / `judge` 的同步调用要改）。
- **C. 内容脚本按页面类型懒加载**：目前在全部 bilibili.com 页面（含首页、搜索）加载 8 个文件并读取 seen / llm；多数用户远低于上限，收益小；动启动路径风险较大。

## 6. 仍需实机确认

- 换页重置：若 B 站切视频是整页刷新而非 SPA，该路径不会触发（无副作用）；若是 SPA，请观察切视频后悬浮台记录是否清空、评论是否被正确重新识别。
- 名单纯新增路径：在两个标签页同时开着评论区时，一个标签页拉黑后，另一个标签页该账号的评论应当立即隐藏。
